# Versioning Policy

Reading Strategy Coach intends to follow Semantic Versioning using the `MAJOR.MINOR.PATCH` format.

- **MAJOR:** Incompatible changes to established application behavior, interfaces, data, or operational expectations.
- **MINOR:** Backward-compatible functionality or substantial new capabilities.
- **PATCH:** Backward-compatible fixes and small improvements.

Version `0.x.x` represents initial development. A version becomes part of release history only after the release has been completed and verified.

---

# Changelog Format

Future release entries should use only the categories applicable to verified changes:

- **Added:** New functionality, documentation, or capabilities.
- **Changed:** Changes to existing behavior, structure, or documentation.
- **Improved:** Enhancements to existing functionality, quality, or process.
- **Fixed:** Corrections to defects or inaccurate documentation.
- **Removed:** Functionality, content, or processes removed from the project.
- **Deprecated:** Supported functionality or processes scheduled for removal.
- **Security:** Security fixes, mitigations, or validated security improvements.

# Documentation Maintenance

All significant architectural, operational, and functional changes should be recorded in this document as part of the project development workflow.

Contributors should:

- Update `Unreleased` when verified changes are completed.
- Move applicable entries into a versioned section when a release is verified.
- Record the verified release date.
- Keep the newest completed release above older releases.
- Omit empty categories from completed release entries.
- Link related architectural decisions when they explain a significant change.
- Avoid using the changelog as a roadmap or list of unapproved work.
