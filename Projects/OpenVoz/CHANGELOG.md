# OpenVoz Changelog

# Purpose

This document records verified changes to the OpenVoz project across releases.

The changelog provides contributors and operators with a concise history of added, changed, fixed, removed, deprecated, and security-related work.

---

# Versioning Strategy

OpenVoz uses Semantic Versioning in the `MAJOR.MINOR.PATCH` format.

## Major Releases

Increment the major version when a release introduces incompatible application, API, data, deployment, or operational changes.

## Minor Releases

Increment the minor version when a release adds backward-compatible application functionality or a substantial new operational capability.

## Patch Releases

Increment the patch version for backward-compatible fixes, maintenance changes, and small operational improvements.

## Documentation-Only Updates

Record documentation-only updates under `Changed`. Include them in the next applicable release or increment the patch version when the documentation update must be released independently.

Version `0.x.x` represents initial development. Version numbers should describe completed and verified work rather than planned changes.

---

# Changelog Format

Each release uses only the categories required for its verified changes.

## Added

New functionality, components, documentation, or operational capabilities.

## Changed

Changes to existing behavior, architecture, procedures, or documentation.

## Fixed

Corrections to defects, incidents, or inaccurate documentation.

## Removed

Functionality, components, procedures, or documentation removed from the project.

## Deprecated

Supported functionality or procedures scheduled for removal in a future verified release.

## Security

Security fixes, mitigations, or validated security improvements.

# Best Practices

- Update the changelog as part of each release.
- Record only completed and verified changes.
- Group changes by release and standard category.
- Write entries from the user, operator, or system perspective.
- Keep entries concise and specific.
- Reference related incident records when a fix resolves a production incident.
- Do not include credentials, personal data, or sensitive infrastructure details.
- Do not use the changelog as a roadmap or list of planned work.
- Assign a release date only when the release date has been verified.
- Keep the newest release entry above older release entries.
